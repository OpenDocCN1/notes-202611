
# 🛡️ Ethical Hacking：50-Day Hacker Challenge：12：传统SQL注入实战教程

![](img/ad2a271b2fc8c4686ac40b8a076792f6_0.png)

在本节课中，我们将一起学习传统SQL注入的核心知识和实际操作方法。传统SQL注入是Web应用安全中最经典、最常见的攻击方式之一，它利用应用程序对用户输入没有进行充分过滤的弱点，把恶意的SQL代码插入到后台数据库查询语句里面。攻击者通过这种方式，可以绕过正常的登录验证，直接从数据库中读取用户名、密码等敏感信息，甚至篡改或删除重要数据。本节课将从最基本的定义讲起，逐步介绍联合查询注入的原理，说明如何利用数据库的元数据表探测表名和列名，讲解如何提取敏感凭证，对比MySQL和PostgreSQL的语法差异，最后通过一个真实靶场案例，完整演示从漏洞探测到获取后台权限的过程。无论你是刚接触Web安全的初学者，还是希望系统复习注入原理的学习者，都能从中获得实用的知识。

## 🔍 Ethical Hacking：50-Day Hacker Challenge：12：SQL注入基础定义

SQL注入的核心概念可以用下面的公式来描述：

![](img/ad2a271b2fc8c4686ac40b8a076792f6_4.png)

```text
SQL注入 = 用户可控输入 + 未经过滤的数据库查询拼接
```

一个简单的正常查询示例如下：

```sql
SELECT * FROM users WHERE id = '用户输入'
```

当应用程序直接把用户输入拼接进SQL语句，而没有做任何安全检查时，攻击者就可以在输入框里提交自己的SQL代码，改变原本查询的逻辑。比如说，原本程序想要根据用户ID查询一条用户记录，攻击者却可以通过构造特殊输入，让数据库返回整个用户表的所有内容，或者执行其他未经授权的操作。传统SQL注入主要针对的是数据库查询字段，攻击者的目标通常是拿到数据库里存储的敏感数据，比如用户名、密码、邮箱地址，甚至是支付信息。这种攻击之所以危险，是因为它不需要复杂的工具，只需要一个普通的浏览器和对SQL语法的基本理解，就有可能造成严重的数据泄露。

- 财务记录和交易明细

## 🛠️ Ethical Hacking：50-Day Hacker Challenge：12：联合查询注入原理

联合查询注入是传统SQL注入中最经典、最实用的一种手段。它的核心原理可以用下面的代码结构来表示：

![](img/ad2a271b2fc8c4686ac40b8a076792f6_23.png)

```sql
UNION SELECT 1,2,column_name FROM information_schema.tables WHERE table_name='users'
```

![](img/ad2a271b2fc8c4686ac40b8a076792f6_25.png)

攻击者利用SQL语言中的UNION关键字，把自己构造的查询结果和原始查询结果拼接在一起，返回给应用程序页面。这样一来，页面上就会显示出本来不应该出现的数据库内容。具体操作时，攻击者通常需要先猜出原查询语句返回的列数，然后通过输入类似UNION SELECT 1,2这样的测试语句，探测哪些列的内容可以在页面上回显。一旦确定了可以显示数据的列位置，攻击者就把这些位置替换成真正想要查询的数据库名、表名或者列名，从而把敏感数据直接显示在网页上。

![](img/ad2a271b2fc8c4686ac40b8a076792f6_26.png)

![](img/ad2a271b2fc8c4686ac40b8a076792f6_27.png)

联合查询注入的常见操作步骤如下：

![](img/ad2a271b2fc8c4686ac40b8a076792f6_29.png)

![](img/ad2a271b2fc8c4686ac40b8a076792f6_30.png)

1. 输入测试字符，观察页面是否报错或返回异常
2. 使用ORDER BY或UNION SELECT确定查询列数
3. 找出可以在页面上显示数据的列位置
4. 将可显示位置替换为数据库、表名或列名
5. 提取目标数据并显示在页面上

![](img/ad2a271b2fc8c4686ac40b8a076792f6_31.png)

![](img/ad2a271b2fc8c4686ac40b8a076792f6_32.png)

## 📊 Ethical Hacking：50-Day Hacker Challenge：12：从数据库元数据提取表与列

在实际攻击场景中，攻击者很少能直接知道目标数据库的表结构。为了找到存储敏感数据的表，攻击者通常会查询数据库自带的元数据表，也就是information_schema。常用的查询语句如下：

![](img/ad2a271b2fc8c4686ac40b8a076792f6_34.png)

```sql
SELECT table_name FROM information_schema.tables WHERE table_schema='数据库名'
SELECT column_name FROM information_schema.columns WHERE table_name='users'
```

information_schema里面记录了当前数据库的所有表名和列名，相当于数据库的目录索引。攻击者可以先查询information_schema.tables，找出名为users、admin或者customer之类的可疑表。确定了目标表之后，再查询information_schema.columns，找出用户名、密码、邮箱等敏感列的具体名称。有了表名和列名，攻击者就可以编写精确的查询语句，把这些表里的数据一行一行地拖出来。

以下是information_schema中常用的查询示例：

![](img/ad2a271b2fc8c4686ac40b8a076792f6_36.png)

![](img/ad2a271b2fc8c4686ac40b8a076792f6_37.png)

- 查询当前数据库下的所有表名
- 查询指定表中的所有列名
- 筛选表名中包含user、admin或member的表
- 查询列名中包含password、email或credit的字段

通过元数据探测，攻击者就能把数据库的结构摸清楚，为下一步提取具体的账号密码做好准备。

## 🔑 Ethical Hacking：50-Day Hacker Challenge：12：提取敏感凭证数据

![](img/ad2a271b2fc8c4686ac40b8a076792f6_39.png)

当攻击者已经知道了目标表名和列名之后，接下来就是提取具体数据的阶段了。最常见的目标就是用户表里的账号和密码，对应的查询语句通常如下：

![](img/ad2a271b2fc8c4686ac40b8a076792f6_41.png)

```sql
SELECT username, password FROM users
```

![](img/ad2a271b2fc8c4686ac40b8a076792f6_43.png)

有些场景下，攻击者还会使用数据库特有的报错函数，强制数据库在报错信息里把查询结果暴露出来。例如在MySQL中，可以使用EXTRACTVALUE函数来配合注入攻击，让数据库在处理异常时把数据泄露在错误信息中。无论使用联合查询还是报错注入，攻击者的最终目的都是一样的，就是从数据库里把用户名、密码、会话令牌等敏感凭证拖出来。拿到这些信息之后，攻击者就可以尝试登录其他用户的账户，或者直接进入后台管理系统，获取更高的系统权限。

攻击者经常重点攻击的数据库表包括以下几类：

- users表：存储普通用户的账号和密码
- admin表：存储管理员后台的登录凭证
- customer表：存储客户订单和个人联系信息
- session表：存储用户登录会话和令牌数据

数据提取完成后，攻击者就掌握了进入系统的钥匙，接下来我们看看不同数据库之间的语法差异，因为现实中的目标不一定全是MySQL。

## 🐘 Ethical Hacking：50-Day Hacker Challenge：12：PostgreSQL的特殊差异

虽然很多Web应用使用MySQL，但也不少系统采用PostgreSQL数据库。这两种数据库在SQL语法上存在关键差异，攻击者在编写注入语句时需要特别注意。常见的语法对比如下：

```text
MySQL多行合并：GROUP_CONCAT(column_name, ',')
PostgreSQL多行合并：STRING_AGG(column_name, ',')
```

![](img/ad2a271b2fc8c4686ac40b8a076792f6_47.png)

MySQL常用GROUP_CONCAT把多行查询结果合并成一行字符串，方便在注入结果里一次性看到多条数据。而PostgreSQL没有GROUP_CONCAT这个函数，通常需要用STRING_AGG来实现类似效果。另外，在分页和偏移量方面，PostgreSQL的OFFSET语法也与MySQL略有不同，攻击者需要根据实际数据库类型调整注入负载，才能成功提取数据。除此之外，两种数据库的系统表名称、元数据查询方式也存在差异，不能直接通用。

![](img/ad2a271b2fc8c4686ac40b8a076792f6_49.png)

MySQL与PostgreSQL在注入场景下的常见差异包括以下几点：

- 多行结果合并函数名称不同
- 分页限制和偏移量语法有细微差别
- 元数据信息存储的系统表不完全相同
- 报错函数和特有函数的支持情况不同

了解这些差异之后，攻击者在面对不同类型的目标时，就能选择合适的注入技巧。接下来，我们进入最实用的部分，通过真实靶场来演示整个攻击流程。

## 🏛️ Ethical Hacking：50-Day Hacker Challenge：12：真实靶场渗透演示

![](img/ad2a271b2fc8c4686ac40b8a076792f6_51.png)

理论学习之后，最关键的是把知识应用到实际场景中。本节我们将通过一个模拟的政府系统靶场进行演示，这个靶场模拟了某国家基础设施保护相关网站。在渗透测试中，攻击者通常会在URL参数里测试类似?id=10这样的输入点，观察页面响应，确认是否存在SQL注入漏洞。确认注入点之后，攻击者会尝试构造联合查询语句，绕过原有的查询逻辑，直接从后台数据库的admin表里提取管理员的用户名和密码。对应的测试负载可能如下：

![](img/ad2a271b2fc8c4686ac40b8a076792f6_53.png)

```text
?id=10' UNION SELECT username, password FROM admin--
```

拿到管理员凭证之后，攻击者就可以直接登录后台管理页面，获取更高权限，甚至进一步控制整个服务器。整个过程完整还原了从漏洞探测到权限获取的攻击链条。

![](img/ad2a271b2fc8c4686ac40b8a076792f6_55.png)

![](img/ad2a271b2fc8c4686ac40b8a076792f6_56.png)

真实靶场渗透测试的主要步骤如下：

1. 在URL参数或表单输入中测试注入点
2. 确认目标使用的数据库类型和版本
3. 构造联合查询负载，提取管理员账号密码
4. 使用获取的凭证登录后台管理系统
5. 记录测试结果，提交漏洞报告

![](img/ad2a271b2fc8c4686ac40b8a076792f6_58.png)

通过这个靶场演示，我们可以看到传统SQL注入在现实环境中的威胁，也理解了为什么在开发Web应用时，必须对所有用户输入进行严格的过滤和参数化查询。
