

# 🔐 FastAPI Masterclass：第130节：什么是身份认证

在本节课中，我们将要学习身份认证的基本概念。本节属于课程的认证部分，重点回答一个非常基础的问题：当客户端或用户向 API 发送请求时，系统如何知道对方是谁。我们还会区分身份认证和授权这两个容易混淆的词，介绍基于令牌的认证方式，并说明本节后续的实战计划。下面先给出核心概念，让初学者建立整体印象。

```text
认证 = 验证(用户身份)
授权 = 检查(已认证身份，允许执行的动作)
```

## 🧩 FastAPI Masterclass：第130节：认证的基本定义

上一节我们说明了本节的主题，本节中我们来看看认证到底是什么意思。认证是把用户登录到系统中的动作，它回答的问题是“你是谁”。当客户端或用户向 API 发送请求时，认证就是验证他们身份的过程。现实中的问题可以这样理解：`bob@example.com` 是不是系统中的真实用户或真实邮箱，这个用户是否提供了与该邮箱凭据匹配的正确密码。如果这些条件都满足，认证就会授予用户使用系统的访问权。

> 认证回答的是“你是谁”。

## ⚖️ FastAPI Masterclass：第130节：认证与授权的区别

上一节我们介绍了认证的定义，本节中我们来看看与它互补的另一个词：授权。授权和认证两个词很像，但含义不同。授权是在用户完成认证之后，允许或禁止该用户执行某个动作。也就是说，认证回答“你是谁”，授权回答“你被允许做什么”。授权来自 authority 这个词，表示用户在我们的系统中拥有什么权限。通常先进行认证，用户先登录，然后即使已经登录，也有一些动作应该被允许，另一些动作不应该被允许。授权可以回答这样的现实问题：Bob 登录后是否有权限删除一条记录、查看一条记录、更新一条记录。

以下是认证与授权的核心区别，初学者可以先记住这两句话。

- 认证：验证用户身份，回答“你是谁”。
- 授权：检查用户权限，回答“你能做什么”。
- 认证通常发生在前面，用户先登录。
- 授权通常发生在认证之后，决定已登录用户能执行哪些动作。
- 授权依赖权限体系，例如某个角色是否拥有删除、查看、更新记录的权限。

> 认证先确认身份，授权再检查权限。

## 🎫 FastAPI Masterclass：第130节：令牌认证与常见策略

上一节我们区分了认证和授权，本节中我们来看看认证策略。认证有很多不同策略，很多现代 API 使用一种叫作基于令牌认证的策略。令牌从技术上说就是一个字符串，但它根本上代表一种凭据。客户端在认证成功之后，会在每个请求中发送这个凭据，用来证明自己确实已经通过认证。常见的认证策略包括会话、OAuth、API 密钥等，本课程会聚焦基于令牌的认证。不同策略都有自己的取舍、优点和缺点，本节不认为基于令牌的认证一定最好，也不认为它没有弱点，它是一种现代且流行的做法，常用于 API 或微服务架构中，因为同一个令牌可以适用于多个不同的后端或服务。

以下是原文提到的常见认证策略，了解它们有助于建立全局视角。

- 会话认证：服务器保存登录状态。
- OAuth：一种常见的授权与认证框架。
- API 密钥：用密钥表示调用方身份。
- 基于令牌认证：客户端登录后拿到令牌，后续请求携带令牌。

> 令牌本质上是一个表示凭据的字符串。

## 🔄 FastAPI Masterclass：第130节：令牌认证流程

上一节我们介绍了令牌认证的定位，本节中我们来看看它在高层面的流程。第一步，客户端发送自己的凭据，例如邮箱和密码，把这些信息提交给某个端点。在该端点，服务器验证凭据，确保邮箱匹配数据库中的用户，并确认密码有效。服务器会执行一系列逻辑操作，验证用户确实真实且合法。如果凭据有效，服务器会创建并返回一个令牌。这个令牌是一个普通字符串，代表用户的身份。每个用户都会有一个唯一令牌；如果用户登出后再次登录，会得到一个新令牌；令牌通常还带有时间属性，即使同一个用户相隔一秒登录，也会得到不同的令牌。因此，令牌可以看作唯一标识该用户的字符串，不应该有两个用户拥有完全相同的令牌。

服务器从登录端点把令牌返回给客户端。之后，客户端在每个后续请求中都要包含同一个令牌，通常把令牌附加在请求头中。具体如何存储令牌由客户端自己选择，后端或 FastAPI 并不关心客户端把令牌存在哪里，只期望在登录后的每个后续请求中收到令牌。服务器在每个请求中查找令牌，通常从客户端发来的请求头中解析令牌，并验证令牌的合法性。服务器会确认令牌没有被篡改，确实是当初发给用户的原始令牌。如果攻击者试图篡改或恶意修改令牌，服务器可以发现令牌不是原始令牌，并立即禁止该动作。因为每个用户都有不同的唯一令牌，令牌也能标识是谁在发起请求，也就是标识已经认证的用户或客户端。

以下是令牌认证流程中的关键步骤，便于理解客户端和服务器各自做什么。

- 客户端把邮箱和密码等凭据发送到登录端点。
- 服务器验证邮箱是否匹配数据库用户，并验证密码是否有效。
- 凭据有效时，服务器创建并返回一个唯一令牌。
- 客户端保存令牌，并在后续每个请求中携带同一个令牌。
- 服务器从请求中解析令牌，验证令牌是否合法、是否被篡改。
- 服务器通过令牌识别请求者，并确认该请求来自已认证用户。
- 令牌过期后，服务器要求客户端重新登录并获取新令牌。

```text
token = login(email, password)

# 后续请求
Authorization: Bearer <token>
```

关键点是：登录后，客户端必须在每个后续请求中附加令牌。如果某个请求没有附带令牌，服务器会认为客户端未认证，要求用户重新登录以获取新令牌，然后继续期望后续请求携带令牌。服务器信任客户端在每次请求、每次访问服务器时提供令牌，以便验证客户端已经认证。此外，令牌会随着时间过期。服务器可以把过期细节嵌入令牌字符串本身，相当于在令牌中写入过期时间，服务器每次收到令牌都会验证。令牌过期后，访问权限失效，服务器会表示令牌已过期，要求用户重新登录。可以认为令牌就是一把钥匙，允许客户端在初始登录后访问服务器并发送后续请求。

## 🫥 FastAPI Masterclass：第130节：无状态认证

上一节我们走完了令牌流程，本节中我们来看看无状态这个概念。基于令牌的认证可以被视为无状态认证。无状态的意思是，后端不保存用户已登录或已认证的永久状态。服务器不会把登录状态保存到数据库，也不需要去检查某个数据或某个状态来判断用户是否登录。已经认证这件事更像是用户的一种假定状态。请求中携带令牌，就是客户端证明自己已登录的方式。用户已认证或已登录，并不是因为某个数据库这样记录，而只是因为请求中包含令牌。令牌是证明、标记、指示器或标志，表示用户已经登录。客户端有责任持续发送令牌，在每个请求中持续告诉服务器“我已经登录”。

HTTP 是无状态协议，每个请求都是独立的，不会记住之前的请求。这给认证带来一个明显问题：用户登录一次后，通常希望连续执行五个不同动作，而不想反复登录。问题在于，如果每个请求完全独立，如何保持“已经登录”这个状态。解决方式之一是让状态保存在服务器上，例如基于会话的认证，服务器创建数据库行来记录哪些用户已经登录。这不是本课程采用的方式，但它是保持登录状态的一种例子。另一种方式是不采用有状态方案，不在服务器上存储或写入数据，而是使用令牌。令牌是无状态方案，因为服务器不永久保存、不保留登录状态，客户端在每个请求中提供令牌，作为仍然登录的证明。

```text
HTTP 请求 A 不记忆 HTTP 请求 B
登录状态的证明 = 客户端在请求中携带的令牌
```

## ✅ FastAPI Masterclass：第130节：令牌认证的优势

上一节我们解释了无状态，本节中我们来看看令牌认证的优势。一个优势是服务器不需要在每个请求中查询数据库来确认用户是否登录，因为认证是无状态的。服务器只需查看令牌是否存在并验证令牌。这些验证是应用中的运行时逻辑，可以运行在路由处理函数附近，不需要访问数据库。另一个问题是：为什么不每次都发送密码和邮箱，而要发送令牌。原因很直接，每次操作都让用户提供凭据会给用户增加很多负担。即使假设用户愿意反复提供凭据，重复发送密码也更容易带来风险，因为一旦发生拦截，密码可能被黑客发现。令牌通常是临时的，并且会过期；密码则更危险，因为黑客可能利用密码反复访问系统。对于密码这类敏感信息，应该尽量减少发送总次数。令牌相当于一层抽象，它是用户身份的标识，但用户可以每次发送令牌，而不必反复提供密码。

此外，当系统有多个后端或 API 时，它们可以依赖同一个令牌，在多个服务之间认证用户。用户可以在一个位置登录并拿到令牌，然后把令牌提供给多个后端或 API。如果这些服务知道如何相互验证，就可以在多个服务之间认证用户，而不需要用户分别登录每个服务。

以下是令牌认证的主要优势，方便初学者从实际使用角度理解。

- 服务器不必每个请求都查询数据库确认登录状态。
- 服务器只需检查并验证请求中的令牌。
- 客户端不必反复发送密码等敏感凭据。
- 令牌比密码更适合频繁发送，因为令牌通常会过期。
- 同一个令牌可以在多个后端或 API 之间复用。
- 用户登录一次后，可以在多个服务之间使用同一身份凭据。

## 🗺️ FastAPI Masterclass：第130节：本节实战计划

上一节我们总结了令牌认证的优势，本节中我们来看看本节的实战安排。接下来我们不再停留在 rental room 项目中，而是进入一个新项目，在 FastAPI 中从零构建认证系统。第一步是构建登录端点，接受邮箱和密码，并验证这些内容是否有效。服务器会把提交的数据与数据库中的数据进行比较，找到并验证合法用户。认证成功后，服务器会返回一个令牌，具体类型是 JWT。后面会进一步讲解 JWT，它基本上就是一个字符串，包含用户信息、过期日期和一些补充数据，是一串字母数字字符，作为用户标识，用户需要在后续每个请求中提供它。

以下是本节后续的实战步骤，整体路线非常清晰。

- 构建登录端点，接收邮箱和密码并验证合法用户。
- 认证成功后返回 JWT 令牌，作为用户身份标识。
- 保护某些路由，只允许已认证用户访问。
- 观察登出用户被拒绝访问，登录用户可以正常请求。
- 定义基于角色的访问控制，为不同用户角色分配不同权限。
- 例如区分普通用户和管理员，只允许管理员执行某些动作或访问某些路由。

再往后，我们会进入基于角色的访问控制。不同用户类型或角色会拥有不同权限，某些用户有权限执行某些动作，其他用户没有。这会逐渐进入前面提到的授权部分：某些用户可以执行动作，其他用户不可以。例如系统中有普通用户和管理员，只有管理员能执行某些动作或访问某些路由。这个部分内容较多，也很有趣，下一课会继续展开。

## 📌 FastAPI Masterclass：第130节：总结

本节课中，我们一起学习了身份认证的核心概念。认证回答“你是谁”，授权回答“你被允许做什么”。认证通常先发生，用户先登录；授权发生在认证之后，用来检查已登录用户能否执行某个动作。基于令牌的认证是现代 API 中常见的做法，客户端登录后获取令牌，并在后续每个请求中携带令牌，服务器验证令牌并识别用户。令牌认证是无状态的，服务器不保存永久登录状态，客户端持续提供令牌作为已登录证明。令牌还会过期，过期后需要重新登录。最后我们了解了本节的实战计划：构建登录端点、返回 JWT、保护路由、实现基于角色的访问控制。下一课会从代码层面逐步走完整个流程。

> 记住核心：认证确认身份，授权检查权限，令牌是客户端后续请求中的身份证明。
