## 🗂️ FastAPI 大师课：129.1：数据库迁移是什么

前面已经说明本节从数据库迁移开始，这一小节就把迁移的概念讲透。迁移是一个文件，用来描述数据库 schema 的一次变化。schema 可以理解为数据库的表结构、字段结构、约束和索引等整体形状。迁移可以表示增加一列、删除一列、更新某一列的数据，也可以表示增加唯一性约束或增加索引。只要是对数据库 schema 的某种修改，让数据库结构能够随着时间变化和演进，都可以用迁移来描述。

需要注意，迁移文件本身是用编程语言写出来的。在 Python 和 FastAPI 生态里，迁移通常用 Python 编写；在其他编程语言生态里，也会有类似的迁移工具，完成同样的功能。这个功能本质上就是保存一份按时间顺序排列的代码历史，用代码描述数据库 schema 的所有变化。换句话说，迁移记录的是数据库形状随时间变化的过程。

核心概念可以用一个简单公式表示：

```text
新数据库结构 = 应用迁移文件(旧数据库结构)
```

上一小节我们明确了迁移是“描述 schema 变化的文件”，本节中我们来看看 Python 生态里常用的迁移工具 Alembic 如何初始化，以及迁移工作流如何运转。

## ⚙️ FastAPI 大师课：129.2：Alembic 初始化与迁移工作流

在 Python 社区里，SQLAlchemy ORM 是很流行的标准工具，Alembic 则是它配套的标准迁移工具。每当我们在项目里加入 Alembic 作为依赖后，第一步是先初始化一些起始文件。初始化命令以 `uv run alembic init` 开头，后面的参数用来指定 versions 或 migrations 目录放在哪里。这个目录叫 `alembic` 是常见选择，叫 `versions` 或 `migrations` 也可以，具体会因项目而异。

以下是初始化迁移目录的示例命令：

```bash
uv run alembic init alembic
```

初始化完成后，迁移工作流大致如下。第一步，修改一个或多个模型，例如增加字段、删除字段等，此时变化还只存在于代码里。第二步，运行 Alembic 的 revision 命令，自动创建新的迁移文件。第三步，检查并必要时手动修正迁移文件，然后执行迁移。最关键的地方是加上 `--autogenerate` 设置，让 Alembic 解析模型，找出模型与当前数据库 schema 不同步的地方，并生成让数据库 schema 与当前模型形状同步或更新的迁移。还需要加上 `-m`，它是 message 的缩写，用来给这次 revision 附加说明消息。Alembic 会把生成的迁移放进 versions 目录。

以下是自动生成迁移文件的典型命令：

```bash
uv run alembic revision --autogenerate -m "add user email column"
```

每个迁移都会有一个唯一标识。随着迁移数量增加，从文件顶部往底部看，每一个迁移还会引用它前面紧挨着的那个迁移，也就是队列里上一个迁移。Alembic 在背后利用这些引用关系，追踪迁移的顺序或迁移链，从而知道要按什么顺序运行迁移，最终把数据库 schema 带到当前最新的形状。理解这一点很重要，因为迁移不是孤立文件，而是一条有先后关系的变更链。

上一小节我们了解了迁移如何生成以及迁移链如何组织，本节中我们来看看生成迁移后为什么必须检查，以及模板文件能做什么。

## 🔍 FastAPI 大师课：129.3：检查迁移与模板

生成迁移文件后，始终要再次检查迁移文件是否准确，因为 Alembic 可能犯错，并不总能自动得到完全正确的结果。一个著名例子是重命名列：Alembic 可能误以为你删除了旧列并新增了一个新列。遇到这种情况，就需要打开迁移代码，把自动生成的内容改写成真正正确的迁移逻辑，手动写出准确的迁移代码，确保数据库得到正确的更新。

以下是使用迁移时需要记住的几条实践：

- 迁移文件要跟着项目一起提交，不要把迁移排除在版本控制之外。

- 编辑迁移文件并不是坏事，但更好的习惯是让自动生成尽量完成大部分工作，然后按需修改。

- 可以更新 `script.py.mako` 模板文件，它相当于未来迁移文件的蓝图或模板。

- 如果发现某些 import 或其他代码片段经常出现，可以把它们加到模板里，Alembic 之后生成新迁移时就会自动带上这些内容。

上一小节我们强调了检查迁移和利用模板，本节中我们来看看迁移文件生成后如何真正执行，以及如何向前升级和向后降级。

## ⬆️ FastAPI 大师课：129.4：升级与降级迁移

迁移文件只是一份计划中的变更，数据库不会仅仅因为你创建了迁移文件就自动更新。下一步才是关键动作：真正运行迁移或升级 schema。执行升级时运行 `uv run alembic upgrade`，后面可以跟不同参数。提供 `head` 会运行所有尚未执行的待处理迁移，可能是一个、五个或一百个，但 `head` 总会把你带到最新迁移，也就是 schema 的最新状态。也可以提供类似 `+1` 或 `+2` 的数字，向前升级指定数量的迁移。例如有五个待处理迁移，但你只想运行其中三个，就可以提供 `+3`。另一种方式是跟上某个迁移的唯一 ID，这个 ID 既能在文件名里找到，也能在迁移文件内部找到。

以下是常用的升级命令示例：

```bash
uv run alembic upgrade head
uv run alembic upgrade +3
uv run alembic upgrade <migration_id>
```

迁移的一个关键优势是既能向前走，也能向后退，回到过去某个时间点或某个版本的数据库 schema。升级表示向前移动，降级表示回退或向后移动。对应的降级命令是 `uv run alembic downgrade`，在 uv 项目里同样要加上 `uv run`。`uv run alembic downgrade -1` 会回滚上一个迁移；也可以自定义数字来一次回退多个迁移，例如 `-3` 会回滚或还原最后三个迁移。每个迁移文件里都有两个互补函数：`upgrade()` 和 `downgrade()`。`downgrade()` 描述如何反转或撤销 `upgrade()` 带来的变化，所以这两个函数都必须存在，Alembic 这样的工具才知道如何在按时间排列的检查点或保存点之间前后移动，这些检查点就是迁移。降级时也可以提供具体的迁移 ID，降级到指定版本，和升级命令类似。最后，如果想一路回到最开始、任何迁移运行之前的 schema 起点，可以运行 `uv run alembic downgrade base`，它会回滚所有迁移。

以下是常用的降级命令示例：

```bash
uv run alembic downgrade -1
uv run alembic downgrade -3
uv run alembic downgrade <migration_id>
uv run alembic downgrade base
```

上一小节我们讲完了迁移的升级和降级，本节中我们来看看数据库事务，它关注的是一组操作如何整体提交或整体回滚。

## 🔄 FastAPI 大师课：129.5：数据库事务

数据库事务可以理解为一个工作集合，或者一个分组，里面包含多个操作。事务的优势在于，它像一个管理者，监督你要应用到数据库上的整个操作过程。事务不一定必须包含多个操作，也可以只包住一段代码顺序，或者只包住一条数据库命令。事务的核心作用是：要么提交变更，把工作保存并持久化到数据库；要么在出错时回滚事务，撤销这些变更。

例如，一个事务里包含五次插入操作。如果第四行或第五行插入失败，你可能希望把已经成功插入的前三行也回滚掉，让整个过程像没有发生过一样。事务就是这样一个组织容器，让操作要么成功向前，要么失败回滚，避免进入奇怪状态。比如一张表里的记录已经创建成功，但后续插入失败，你可能并不希望这些前面创建的记录继续存在。使用事务就可以避免这种场景。

核心逻辑可以用下面的伪代码表示：

```python
with session.begin():
    session.add(record1)
    session.add(record2)
    # 任意一步失败，整个事务回滚
```

好消息是，SQLAlchemy 提供的 session 对象会在背后自动创建事务。因此通常会用 Python 上下文管理器 `with` 把相关操作包起来，因为它会在背后处理这些复杂细节。如果代码遇到运行时错误或异常，它会自动回滚事务，确保数据库里不会留下坏记录。事务实际上实现的是全有或全无的变更序列：要么全部应用到数据库，要么全部回滚。

以下是事务的两种典型结果：

- 提交：把变更保存并持久化到数据库。

- 回滚：撤销变更，让数据库回到事务开始前的状态。

上一小节我们从事务角度理解了全有或全无，本节中我们来看看数据库索引如何加速查询，以及为什么索引不能无脑加。

## ⚡ FastAPI 大师课：129.6：数据库索引

数据库索引是一种数据结构，用来加速对某一列值的查找和连接操作。它的做法是在背后把相关值存到单独的数据结构中，并记录这些值出现的位置。可以把它类比成学术书籍末尾的索引：书末索引记录某些词在整本书里出现的位置，数据库索引则记录某些列值在表里出现的位置。数据库在增加或删除行时，会花时间更新索引，以便知道某个给定 ID 在某一列中出现的所有位置，以及确切出现在哪些行里。

举个例子，假设外键值 5 在第 10 行被引用，又在第 10000 行被引用。你不希望某个查询为了找到这两行而按顺序扫描全部 10000 行。索引会记录“外键 5 出现在这些行里”这类信息，并把这些数据放在单独的数据结构里。这样数据库定位目标行会容易很多，不需要逐行重新扫描。当然，索引背后还有很多复杂机制，这里讲的是基本工作原理。

以下是索引的收益和代价：

- 收益：加速频繁用于查询和连接的列值查找。

- 代价：增加、更新、删除行时，索引也要更新，写操作会变慢。

- 原则：索引通常是好模式，但要相对节制地使用。

- 适用对象：频繁作为查询条件或连接条件的列，例如外键。

很多初学者会问，为什么不给每一列都加索引。答案在于“过度”二字。索引加得太多，反而会拖慢数据库，尤其是写操作，例如更新和删除。因为只要这些操作发生，索引就要同步更新。假设一张表有 20 列，20 列都有索引，那么每次增加一行，20 个索引都要更新，数据库就会逐渐变慢。索引一般是不错的模式，但应该用在经常被查询或连接的列上。外键就是明显例子，因为外键在查询里用得多，在连接里也用得多，很适合创建索引。

在 SQLModel 中，给字段加索引只需要在字段上添加 `index` 参数并设为 `True`，然后生成一个新迁移，迁移会自动创建索引，数据库会在背后处理复杂细节。我们还讲了 `unique` 参数，它会要求数据库应用唯一性约束。唯一性约束在真实业务里很有价值，例如邮箱或用户名。这里有一个有意思的点：唯一性约束会自动创建索引。

核心概念可以用下面代码表示：

```python
from sqlmodel import Field, SQLModel

class User(SQLModel, table=True):
    id: int | None = Field(default=None, primary_key=True)
    email: str = Field(index=True, unique=True)
```

上一小节我们讲完了索引的收益、代价和 SQLModel 写法，本节中我们对整节内容做最后总结。
