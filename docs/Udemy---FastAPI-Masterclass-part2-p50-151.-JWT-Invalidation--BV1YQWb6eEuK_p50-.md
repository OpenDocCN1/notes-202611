
# 🔐 FastAPI Masterclass Part 2：第151节：JWT 失效

本节课中，我们要学习的是JWT失效问题，以及JWT在无状态认证体系下所固有的一些弱点。我们会先回顾一下无状态认证是什么意思，再看看当我们想要让用户提前登出时会遇到什么困境。然后我们会介绍“快乐路径”，也就是正常用户主动登出的情况，接着进入“不快乐路径”，也就是黑客拿到用户JWT后的应对策略。最后我们会总结出一种常见的解决方案：在后端保存一个“已撤销JWT”的集合，并讨论它带来的性能和安全性上的权衡。通过这节课，你会明白为什么JWT的无状态特性既是优点也是挑战，以及如何在需要时手动让一个还未过期的JWT失效。

## 1️⃣ 回顾：JWT 的无状态认证

如我们目前已经看到的，JWT在设计上就是无状态的，它能提供无状态认证。这里所说的“无状态”，指的是后端、服务器这一侧。也就是说，我们的FastAPI应用不会在任意地方存储任何信息，也不会持久化任何状态。举例来说，在本课程的这一部分，我们没有创建任何数据库表，也没有向任何数据集合里写入数据，以便后续参考。相反，真正承担认证证明作用的，是令牌本身——客户端在每一个请求中携带的JWT。客户端每发一次请求，就在请求头中带上这个JWT，后端通过它来判断请求者是否已经通过认证。

因此，“已通过认证”这个状态更像是某种瞬时的想法，它没有被保存在任何地方。我们并没有一张用户表，用于记录哪个用户当前已经登录、哪个用户当前已经注销。在这种情况下，用户被迫重新登录的唯一机制，基本上就是他的令牌失效了。例如，令牌不是一个合法的令牌，或者令牌已经过期了，而过期信息被打包并编码在令牌本身内部。只要这个JWT还是有效的，用户就可以一直用它访问，直到它过期为止。这就是无状态认证的基本工作方式。

用公式来描述就是：

`认证状态 = 客户端提供的 JWT 是否有效 && 是否未过期`

## 2️⃣ 问题：想要提前登出怎么办？

正是因为JWT是无状态的，一个有趣的场景就出现了。假设用户有一个10分钟的令牌有效期窗口，但我们想在10分钟结束之前就让该用户登出，我们该怎么做？我们不能删除一个JWT，也不能在后端或服务器上删除任何关于“该用户已登录”的状态信息，因为服务器根本没有保存这些信息。我们之前也没有把JWT保存到任何其他端点，我们只是简单地把JWT发回给客户端，让客户端可以在后续请求中继续使用它。令牌一旦发出去，服务器手里就没有副本了。

这样就产生了一个非常棘手的问题：如果我们希望某个用户退出登录，或者因为在恶意行为者的情况下要强制他退出登录，我们实际上没有任何后端状态可以用来做这件事。你可能会认为，让客户端删掉本地令牌就可以了。但这里讨论的场景中，恶意攻击者是不会主动删除令牌的。所以，真正的挑战在于：服务器这边没有保存状态，就无法主动去让某个令牌失效。这正是JWT无状态特性带来的一大局限。接下来，我们先看看正常情况下的退出登录是怎么处理的。

## 3️⃣ 快乐路径：客户端主动删除令牌

让我们先来聊聊“快乐路径”，也就是一切正常运转时的情形。一会儿我们才会讲到黑客，现在只考虑普通的、遵守规则的好用户，也就是那些按照我们预期的方式使用应用的人。在JWT的典型策略中，负责让用户退出登录的通常是客户端，而不是后端。这个责任分配是很合理的，因为客户端才是保存和携带令牌的一方。

举个例子，在你的前端应用里，比如一个React应用，你可能会有一个“退出登录”按钮。当用户点击这个按钮时，前端也就是客户端要做的事情非常简单：删除它本地存储的JWT或访问令牌。删掉之后，在后续的请求中，它自然就无法在Authorization请求头里提供这个令牌了。换句话说，这个令牌不会再被发送到后端。因为Authorization头中不再有JWT，后端的FastAPI应用也就会检测到用户处于未认证状态，从而要求用户重新登录。

具体流程可以概括成下面的列表：

- 前端在用户登录后保存JWT，并在每次后续请求时把它放在 Authorization 头中。
- 用户点击“退出登录”按钮，前端删除本地存储的JWT。
- 后续请求不再携带JWT，后端发现没有令牌，就认为用户未认证，强制其重新登录。

所以，说到底这是客户端的责任。为什么会这样？因为客户端是那个需要为所有后续请求保存JWT的组件，也只有客户端能在本地清除或删除这个令牌。后端是不知情的，它只是把令牌当作认证证明。最终是客户端在每次请求时保存和发送令牌，因此只要客户端应用在用户点击退出时处理令牌的删除，我们实际上就是依靠前端来实现用户登出。在理想情况下，这个方案运行得很完美。这就是我们所说的“快乐路径”——系统中的每个部分都在按部就班地协同工作，你的FastAPI后端和前端应用为了用户的利益而互相配合。

显然，如果你是一个后端开发者，并且你在和同公司的前端开发者沟通，你们有共同的利益，那就是确保代码库对你们自己、对用户、对公司来说都能正常运作。你不会故意引入恶意代码，前端同事也不会，所以你们只需要简单沟通一下，约定好“退出时由前端删令牌”，就可以实现顺畅的用户登出体验。

## 4️⃣ 不快乐路径：黑客拿到了有效 JWT

当一切都在按预期进行时，登出确实不是什么大问题。但真正的挑战出现在“不快乐路径”上，那就是恶意行为者或黑客获得了某个用户的JWT。这个JWT本身可能完全有效，它最初由服务器签名，并作为认证证明发给了用户。但是，如果黑客能够找到并窃取这个JWT，那么即便这个JWT是有效的，黑客也可以冒充那位用户，向服务器发出请求，然后实施一些恶意操作。服务器并不会知道请求背后的人到底是不是合法用户，它只看令牌是否有效。

这里有一个好消息：我们通常会给JWT设置一个较短的过期时间。所以，只要黑客拿到的只是访问令牌，而没有获得刷新令牌，那么他能够造成的破坏是有限的。毕竟10分钟一到，这个令牌就自然失效了。不过，这依然引出一个根本问题：假设在10分钟的有效期里，第1分钟我们就发现黑客已经拿到了某个用户的JWT，我们是否还能从安全角度采取额外的行动，来使这个JWT失效，并强制那个恶意行为者登出？因为黑客手里现在拿着一个完全有效的用户JWT，我们不希望这个JWT继续被用来向服务器发送有效请求。我们当然想阻止他，但按照目前的无状态设计，服务器上没有任何记录，要怎么阻止？

如果后端需要在JWT自然过期之前撤销它，那么后端就**必须**引入某种形式的服务端状态。没有其他方法能够提供这种额外的安全性，因为你需要一种方式来持久化或保存状态，也就是要保存某种记录，例如“这个用户已经登录了”，以便之后能够使这条记录失效。如果不保存这种状态，JWT就完全是无状态的，服务器上什么也没有，自然也就没有办法在时间耗尽之前让它失效。服务端状态，是“提前作废”的唯一钥匙。

## 5️⃣ 解决方案：保存一个“已撤销 JWT”集合

社区里其实有很多不同的方法来解决这个问题，但它们全部都会涉及同一个思想：在后端的某个永久集合中存储信息。这个集合可以是一个数据库表，也可以是一个更简单的内存数据库，比如Redis。下面我给出一个具体的实现例子。这个例子只是众多方案中的一种，但它能很好地说明如何通过服务端状态来手动撤销JWT。

实现这个方案的关键步骤大致如下：

- 创建一个表或集合，专门用来存放“已撤销JWT”。这些JWT已经被手动失效，不再被允许访问系统。
- 如果我们在10分钟有效期的第1分钟发现某个JWT被泄露、被黑客偷走，我们就可以把这个JWT放入撤销集合中。实际操作中，后端开发人员可以访问数据库，或者通过一个管理端点来添加这条记录。
- 在此之后，每次请求到达服务器时，我们可以在一个依赖注入函数中，接收用户的JWT，并检查它是否存在于撤销集合中。如果不存在，请求才允许继续；如果存在，就拒绝访问。

用公式表示，请求的放行条件就是：

`允许请求 = 签名有效 && 未过期 && JWT不在撤销集合中`

用伪代码可以写成：

```python
def verify_token_not_revoked(jwt_token, revoked_collection):
    if jwt_token in revoked_collection:
        raise HTTPException(status_code=401, detail="Token has been revoked")
    # 其他验证继续...
```

换句话说，我们开始保存状态了。我们正在把一些东西持久化到数据库或后端某个永久数据集合中，以便我们可以知道并跟踪一个令牌是否已被撤销。这样一来，后端的数据、后端的状态成为了确定JWT是否有效的真相来源。虽然原来的JWT本身仍然是由服务器签名且未过期的，但通过添加这个初始检查，我们能够主动使一个本来“有效”的令牌失效。现在我们可以告诉系统：“不行，我们知道这个令牌是恶意的，它就在撤销集合里，是我们手动添加的。”于是系统就会拒绝这个令牌的访问权，黑客也就无法再利用它了。

## 6️⃣ 权衡与取舍

当然，这种做法并非没有代价。如果我们采用撤销集合方案，那么现在每一个请求都必须访问某种数据库，去验证令牌是否被撤销。任何数据库访问，一般都会在一定程度上增加延迟，拖慢端点的响应速度。所以在设计时，你需要考虑到这种开销。

具体取舍取决于你想要多严格的安全等级，也取决于应用本身的性质。这里有两个对比场景：

- 如果你的应用只供公司内部用户使用，或者用户在里面能做的都不是什么危险的事情。例如，应用只是用来阅读和创建博客文章，那么即使黑客拿到JWT，最坏情况也就是在10分钟内创建一堆博客文章，危害并不大。这种情况下，也许你就不需要引入更复杂的服务端状态方案来撤销JWT，让客户端删令牌的简单方案就够了。
- 反过来，如果你开发的是关键金融应用，必须尽可能防止黑客造成任何损害，并且你能够很快识别出被盗的JWT，及时把它们撤销，那么这类服务端状态方案就变得非常重要，值得引入到你的代码库中。

所以，一如既往，答案取决于你在构建什么，也取决于项目的安全和合规要求。请记住，本节幻灯片里给出的撤销集合方案只是你能实现的解决方案之一。社区中还有很多其他方案，你可以自己去研究它们的各种优缺点。但最后你会发现，所有这类方案都离不开一个核心：引入某种服务端状态，某种永久记录，用来保存信息，好让我们能够在JWT自然过期之前主动让它失效。没有服务端状态，就做不到这一点。

## 总结

本节课中，我们一起学习了JWT失效这个重要主题。我们先回顾了JWT的无状态认证特性，明白了“已认证”这个状态只存在于令牌本身，服务器不保存任何登录状态。接着，我们分析了提前登出时遇到的困难：因为服务器没有状态，所以无法让一个尚未过期的JWT失效。我们还介绍了快乐路径，也就是正常用户通过前端删除令牌来实现登出；也介绍了不快乐路径，也就是黑客持有有效JWT时的风险。针对不快乐路径，我们讨论了通过创建“已撤销JWT”集合来引入服务端状态，从而在JWT过期前强制其失效的方案，并给出了公式和伪代码。最后，我们权衡了该方案的数据库查询开销，并根据应用场景讨论了是否需要采用这种方案。希望这部分内容能帮助你理解JWT的缺陷和补救方法。这节课的内容就到这里，我们下节课再见。
