

# 🎫 FastAPI Masterclass：137：JWT Tokens 教程


在本节课中我们将要学习：当登录端点已经验证用户身份和密码之后，为什么以及如何返回 JWT，并深入理解 JWT 到底是什么、由哪些部分组成、每一部分分别负责什么。课程会把 JWT 从“看起来神秘的字符串”拆成可以直接理解的几个概念，帮助初学者建立完整印象。


## 🧭 FastAPI Masterclass：137：JWT 的基本定位


上一节我们已经把用户验证流程推进到返回令牌这一步，本节中我们来看看这个令牌在系统里的基本定位。在代码当前这个位置，我们有一个令牌端点，它代表用户的登录端点。并且我们已经到达一个点：在证明用户是有效用户、密码也是有效密码之后，我们希望返回 JWT。这个 JWT 就是令牌，换句话说，它是一个字符串，客户端或用户在后续每一次请求中都要提供它，用来向服务器证明自己已经通过认证。


这里先把 JWT 的身份说清楚：JWT 是 JSON Web Token 的缩写。它的目标或它代表的东西，就是把 JSON 转换成令牌。令牌只是一个包含编码后用户信息的字符串。从根本上说，我们是在把用户数据的 JSON 对象、某个载荷或用户相关信息转换成一个字符串，也就是令牌。JWT 只是完成这件事的标准之一。


因此，在后续请求中，用户登录之后会在每次请求里发送 JWT，服务器也会使用这个字符串来识别用户是谁。这里的关键点是用户信息的编码。编码的“编”意味着把信息从一种格式转换成另一种格式。一个合适的同义词是“翻译”。如果把英语翻译成法语，只是从一种语言或一种表示转换到另一种表示。对于 JWT 来说，编码意味着把类似 JSON 对象的东西，本质上相当于包含键值对的 Python 字典，转换成等价的字符串。下面马上会看到例子。


## 🧩 FastAPI Masterclass：137：JWT 的核心定义


上一节我们把 JWT 放到了登录和后续认证的流程里，本节中我们来看看它的核心定义和转换关系。一个 JWT 由三个独立段组成，可以把它们理解为三个部分或三块。这三段之间用点分隔。三段分别是头部、载荷和签名。接下来会逐段详细说明。


先把整体关系写成公式，方便记忆：


```text
JWT = Base64URL(header JSON) + "." + Base64URL(payload JSON) + "." + signature
```


JWT 的三段都使用一种叫 Base64 URL 的编码格式。在这个语境里，编码就是把 JSON 对象转换成等价字符串表示的过程。底层数据没有不同，仍然是同一份信息，只是换了一种翻译方式，几乎像换了一种语言。它之所以叫 Base64，是因为它使用 64 个核心字符。这些字符包括 a 到 z 的小写字母、A 到 Z 的大写字母，一共 52 个，再加上数字 0 到 9，达到 62 个，最后还有短横线和下划线。


它之所以叫 Base64 URL，是因为这 64 个字符不太容易被浏览器或服务器解析时出问题。也就是说，它们是 URL 安全的，在 Web 领域里更不容易制造问题。问题在于，JSON 里其他常见字符，例如花括号、空格、引号或冒号，更容易破坏内容或被错误解析。举个空格相关的例子：假设有一个 Python 字典被转换成等价的 JSON 对象，键和值之间有一个空格、两个空格或 100 个空格。服务器解析客户端载荷，或者客户端解析服务器内容时，由于这种变化很多，解析出错的机会就更大。解析空格和花括号这类符号，比解析连续的字母字符要难得多。


因此这里的目标是使用 64 个对 URL 安全的字符，也就是让浏览器和服务器解析时出错概率更低。因为我们是把包含多个键值对的 JSON 对象建模成一个只使用 64 种可能字符的普通字符串，可用字符更少，所以 Base64 字符串通常会变长。它需要使用额外字符来表示原本更简单的字符，例如一个左花括号也需要用这 64 个可用字符中的某种等价表示。由于只有 64 个字符可用，而需要表示的字符更多，基本上会用这 64 个字符中的一段序列来表示单个字符。因此 Base64 字符串通常比原始数据稍微长一些。


如果不想被这些复杂度困扰，关键结论就是：这是一种从 JSON 对象到只允许使用这 64 个字符的字符串的翻译或转换格式。这里要明确记录一点：Base64 URL 编码不是加密数据，它没有增加任何安全性或安全保护。任何人都可以把 JWT 的头部段和载荷段，也就是前两段，从 Base64 URL 字符串转换回原始 JSON 对象。就像可以从英语翻译成法语，也可以从法语翻译回英语，这里同样可以从 Base64 回到 JSON，这就是解码过程。


这里的关键结论是：我们没有增加额外安全性，只是改变了数据的表示方式。Base64 URL 编码存在，是为了减少令牌传输过程中的解析错误。这一点很重要，因为这个令牌是客户端后续每次请求都要提供的认证证明，后面还要证明用户有权限执行某些操作。正因为这是每个请求都会发送的数据，它需要尽可能稳定，所以才采用这种策略，转换成这种在服务器或客户端都不太容易出错的字符串。


## 🔤 FastAPI Masterclass：137：Base64 URL 的字符集


上一节我们说明了 Base64 URL 的作用，本节中我们来看看它具体使用哪些字符。为了直观看到这 64 个字符的组成，可以把它记成下面这段字符集：


```text
a-z + A-Z + 0-9 + "-" + "_" = 64 个 URL 安全字符
```


以下是这 64 个字符的分类说明：


- 小写字母 a 到 z，共 26 个字符。
- 大写字母 A 到 Z，共 26 个字符。
- 数字 0 到 9，共 10 个字符。
- 短横线 `-` 和下划线 `_`，共 2 个字符。


这四类加起来正好 64 个字符，所以叫 Base64。再加上“URL 安全”这个特点，就形成了 Base64 URL 这个名称。使用这些字符的目的，是让令牌在浏览器和服务器之间传输时更稳定，减少因为空格、花括号、引号、冒号等 JSON 常见字符带来的解析问题。


## 🧱 FastAPI Masterclass：137：JWT 的三段结构


上一节我们理解了编码字符集，本节中我们来看看 JWT 整体的三段结构。在示例里可以看到一个完整 JWT，它由三段组成：头部、载荷和签名。三段之间用点分隔。第一段是头部，中间一段是载荷，最后一段是签名。


为了先建立整体印象，下面把三段结构列出来，后面再逐段拆开：


- 第一段是 Header，也就是头部，用来存放 JWT 的元数据。
- 第二段是 Payload，也就是载荷，用来存放用户数据。
- 第三段是 Signature，也就是签名，用来提供安全验证。


可以把这个结构记成代码形式：


```text
header.payload.signature
```


三段之间用点连接，完整字符串就是客户端之后要保存并在每个请求中发送的令牌。接下来先看第一段 Header。


## 📋 FastAPI Masterclass：137：Header 段


上一节我们看到 JWT 由三段组成，本节中我们来看看第一段 Header 的作用。Header 是 JWT 周围的元数据，它编码或存储关于签名 JWT 所用算法或策略的信息。简单说，就是 JWT 创建方式的说明。这里会有很多不同算法，用来把普通 JSON 对象转换成 JWT，这和前面讲哈希时提到有很多竞争算法是同一个道理。


在左侧可以看到一个 JSON 对象，可以把它理解为 JavaScript 或 JSON 版的 Python 字典。它只是两个键值对的集合：`alg` 是 algorithm 的缩写，表示算法；`typ` 表示令牌类型。编码所做的事情，就是把左侧这个 JSON 对象转换成右侧看到的粗体字符串，更具体地说是第一段字符串，它以 `EY` 开头，以 `J9` 结束。类似下面这样：


```json
{
  "alg": "HS256",
  "typ": "JWT"
}
```


如果改变左侧任意字符，或者增加一个键值对，那么右侧编码得到的 Header 段也会相应改变。因为编码只是翻译层，我们实际上是在把左侧对象转换或翻译成右侧的字符串。头部段负责的是算法和类型这类通用元数据，不具体涉及业务领域或用户信息。


## 📦 FastAPI Masterclass：137：Payload 段


上一节我们拆开了 Header 的元数据，本节中我们来看看第二段 Payload，也就是真正存放用户数据的地方。类似地，左侧有一个 JSON 对象。例如在 FastAPI 应用里，它一开始可以是一个普通字典，由端点返回或打包，然后转换成 JSON 等价形式，再进一步编码成右侧字符串，也就是中间段。Header 存放的是关于算法本身的通用元数据，不专门涉及业务或用户；Payload 才是存放用户数据对象字符串表示的地方。


Payload 里要存哪些属性由我们决定。结合原文，以下是 Payload 中常见的信息类型：


- 用户标识，例如用户 ID 或邮箱。原因是客户端后续请求会发送 JWT，此时用户在技术上已经通过认证，服务器需要解析 JWT 来获取用户凭据，例如 ID 或邮箱，从而知道用户已经登录，并用这些信息执行系统内操作，例如查询记录。
- JWT 签发时间。这个信息告诉用户令牌从什么时候开始生效。
- JWT 过期时间。这个信息告诉用户令牌的有效期限，例如只对接下来 10 分钟有效。


换句话说，用户可以在接下来 10 分钟内被视为已认证。只要令牌没有过期，系统就允许用户执行操作。如果令牌过期，系统就知道用户现在又回到未登录状态，需要提示用户重新登录，从而获得一个新令牌和更长的过期时间。这里的关键结论是：JWT 三段中的第二段字符串叫 Payload，是实际存储用户信息的地方。服务器里可以用普通模型或字典打包信息，FastAPI 把它转换成 JSON，再编码成 Base64 URL 字符串。整个过程仍然是数据转换。


## 🔐 FastAPI Masterclass：137：Signature 段


上一节我们知道了 Payload 存放用户信息，本节中我们来看看第三段 Signature，也就是真正处理安全的部分。Header 和 Payload 前两段是完全可解码的，它们并不被设计成私密或秘密内容。任何人都可以把 Header 元数据或用户 Payload 的 Base64 URL 字符串转换回等价 JSON 对象。但签名是 JWT 字符串或令牌的第三段，它才真正增加安全性。


签名的整体目的，是证明令牌是真实的，并且没有被篡改。换句话说，是证明令牌来自服务器，而不是来自试图从头生成令牌的黑客。为了把安全边界说清楚，下面把三段的可解码性和作用列出来：


- Header 段可解码，存放算法和类型等元数据，不提供安全保护。
- Payload 段可解码，存放用户标识、签发时间、过期时间等信息，不提供安全保护。
- Signature 段用于安全验证，证明令牌真实且未被篡改。


> Base64 URL 编码不是加密，前两段任何人都可以解码；真正的安全来自第三段签名。


下一节课会详细讲这种安全机制如何工作。现在重要的是理解意图：任何恶意黑客如果试图伪造真实 JWT，或者创建一个看起来真实的 JWT，签名就是阻止他们获得高成功概率的关键。因为如果黑客知道 Payload，例如用户邮箱，并且把 JSON 对象转换成等价的 Base64 URL 字符串，他们很容易猜出或伪造第二段，也可以伪造第一段 Header 元数据。但是黑客几乎不可能生成有效 JWT，因为第三段签名会让服务器验证 JWT 是否有效、是否来自服务器、是否确实是真实 JWT。下一节课会继续讨论安全细节。这里的关键结论是：JWT 基本上就是一个字符串，一个令牌。用户登录时，服务器把 JWT 发给客户端，客户端在后续每个请求中提交给服务器，作为用户已认证的证明。


JWT 是一个普通 Base64 URL 编码字符串，是从等价 JSON 对象翻译得到的。Header 决定创建 JWT 所使用的算法，Payload 是包含键值对和用户信息的 JSON 对象。JWT 有三段：Header、Payload 和 Signature。Signature 对安全最重要，但整体上仍然是把一组 JSON 数据翻译成字符串令牌，用户持续发送它来证明自己已经认证。下一节课会讲更多安全内容。


## ✅ FastAPI Masterclass：137：本课总结


到这里，本课关于 JWT 的核心内容已经串起来了，本节中我们来做最后总结。最后把本课的关键结论收拢成下面几点：


- JWT 是 JSON Web Token，目标是把 JSON 用户数据转换成令牌字符串。
- JWT 由 Header、Payload、Signature 三段组成，三段用点分隔。
- 三段都使用 Base64 URL 编码，编码是翻译或转换，不是加密。
- Base64 URL 使用 64 个 URL 安全字符，目的是减少浏览器和服务器解析错误。
- Header 存放算法等元数据，Payload 存放用户标识、签发时间和过期时间等信息。
- Signature 负责安全，用来证明令牌真实且未被篡改。
- 客户端登录后获得 JWT，并在后续每个请求中发送它，服务器用它识别用户并确认认证状态。


本节课中我们一起学习了登录端点返回 JWT 的背景、JWT 作为 JSON 转令牌字符串的本质、Base64 URL 编码的作用和字符集、JWT 三段结构，以及 Header、Payload、Signature 各自负责的内容。核心记忆点是：JWT 是一个 Base64 URL 编码的字符串令牌，由 `header.payload.signature` 组成，前两段可解码，真正的安全来自签名段。
